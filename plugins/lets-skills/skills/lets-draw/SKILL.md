# lets-draw

Input: `docs/design/SOLUTION-DESIGN.md`. Output: `docs/diagrams/<name>.drawio`, one multi page file that is
structurally valid and actually says something. That path, every time.

The session that invokes this skill is the **orchestrator**. It scopes the pages, spawns the branches, holds the
ledgers, merges the parts and reports. It does not draw. Every page is drawn by a generator sub-agent and judged by a
reviewer sub-agent, and those two are never the same agent. If the design is ambiguous about what talks to what, **ask
the user**.

**No `SOLUTION-DESIGN.md`?** An `ARCHITECTURE.md` plus the ADRs is acceptable, and so is any document stating what the
components are and what talks to what. Whatever the source, **read the infrastructure code and check the prose against
it**: design documents go stale, Terraform does not, and where they disagree the code wins and you say so. Nothing to
read at all: stop and invoke `lets-design`. Never draw a plausible answer to an architectural gap, because a diagram
is read as a statement of fact.

## Where the drawing rules live

`reference/drawio.md`, next to this file: format, escaping, icons, containers, label anchors, layout pitch, the CLI,
and what every validator check means. **The generator sub-agent is told to read it first, and this skill does not
restate it.** What follows is the process only.

## The fact this whole skill is built around

**Almost every way of corrupting a `.drawio` file fails silently.** One class of error is loud, an unescaped
`&`. Every other corruption exits 0 and still exports a PNG, having discarded an edge and its label or deleted the
rest of the page. So "it opened" and "it rendered" prove nothing, and the validator is the only thing that knows.

**And the validator is not enough either.** A real run produced a first iteration that passed every check with zero
errors and was visibly broken in a dozen places. A human looking at the render caught it in seconds, the generator
holding its own reasons for every coordinate could not. **A generator cannot review its own output**, so the reviewing
eye is a separate agent with a separate context, in the loop rather than at the end.

**The validator fails on readability, not only on structure.** `node-overlap`, `label-collision`, `font-contrast` and
`background` are errors, so a branch that will not come clean is a page a reader cannot read. That is why the cap
below means something real.

## The shape of a run

Scope the pages, fan out one branch per page in parallel, merge, validate the merged file. Each branch loops:
generate, validate, render, review, ledger, fix.

### 0. Install the utils

The orchestrator does this once, before any branch starts. **Do not assume `${CLAUDE_PLUGIN_ROOT}` is set.** It is
empty in a sub-agent shell, and `cp -R "${CLAUDE_PLUGIN_ROOT}/draw-io-utils" .` then expands to `cp -R /draw-io-utils
.` and fails. Resolve it, fall back to the plugin cache, stop loudly if neither works:

```sh
src="${CLAUDE_PLUGIN_ROOT:-}/draw-io-utils"
[ -d "$src" ] || src=$(find "$HOME/.claude/plugins/cache" -maxdepth 6 -type d \
  -name draw-io-utils -path '*lets-skills*' 2>/dev/null | head -1)
if [ ! -d "$src" ]; then
  echo "draw-io-utils not found (CLAUDE_PLUGIN_ROOT='${CLAUDE_PLUGIN_ROOT:-unset}', nothing \
under ~/.claude/plugins/cache). Ask the user where the lets-skills plugin lives." >&2
  exit 1
fi
[ -d ./draw-io-utils ] || cp -R "$src" ./draw-io-utils
echo "draw-io-utils installed from $src"
```

Dependency free, Node only. Copy it so the repo can run the check itself later, in CI or by hand.

### 1. Scope the pages

The orchestrator reads the design and fixes the page list before anything is drawn. Each page gets a slug, a name, a
one line statement of what it shows, and the components and flows from the design that belong on it. That list is the
branch list and the tab order of the finished file, so decide it once and hold it. See Pages below for the minimum
set. Fixing it up front stops two branches drawing the same flow under two names.

### 2. Fan out one branch per page

One branch per page, all spawned together, independent, not talking to each other. **Every branch owns its own file**,
`docs/diagrams/parts/<page-slug>.drawio`, a single page mxfile. Not a style choice: all pages live in one mxfile, so
parallel branches editing the finished file would clobber each other.

Each generator is handed **an instruction to read `reference/drawio.md` before writing anything**, the page's slug,
name and purpose from step 1, the solution design or the relevant part plus a pointer to the whole, and its ledger if
this is not round one. Nothing else. The slug is the `<diagram id>` and the page name is the `<diagram name>`, both
assigned here, both unique by construction.

### 3. The branch loop

Per round, in this order:

1. **Generate.** The generator sub-agent writes or fixes `parts/<slug>.drawio`. On round one it writes the page. On every later round it fixes, with the whole ledger in hand.
2. **Validate.** `node draw-io-utils/validate-drawio.js docs/diagrams/parts/<slug>.drawio`. Errors go straight back to the generator. Do not render a file with errors, the picture is a lie.
3. **Render.** Export the page to PNG. One page per part file, so the index is always 1.
4. **Review.** A **fresh reviewer sub-agent, spawned new every round, inheriting none of the generator's context**, gets the PNG, the solution design and the ledger. It returns a verdict and ranked findings.
5. **Ledger.** The orchestrator appends the round to `parts/<slug>.findings.md`.
6. **Fix.** Back to step 1 with the ledger, unless the verdict is clean.

A branch stops when its own reviewer returns clean, the run finishes when every branch has, and no branch waits on
another. A fresh reviewer each round costs one spawn and buys the thing the loop exists for: a reviewer that saw round
one's reasoning inherits its blind spot, and one that saw its own verdict defends it. It gets the ledger, which is
findings, not reasoning.

A `PostToolUse` hook on `Write|Edit` runs the same validator and blocks on errors. It is a backstop and it is tool
shaped: a file written by a heredoc or a script does not fire it at all. Not a reason to skip step 2.

### Render

```sh
command -v drawio && drawio -x -f png -o /tmp/<slug>.png --page-index 1 --scale 2 \
  docs/diagrams/parts/<slug>.drawio
```

**No binary?** The loop still runs and the reviewer reads the XML and the design instead of the picture. Say plainly
in the report that no page was seen rendered. A blind reviewer catches a wrong icon name, a missing connection and a
wrong direction, not a label clearing its neighbour by two pixels. Tell the generator to apply the blind tactics:
detail out of edge labels and into nodes, wider pitch, staggered offsets, split the page.

### 4. The cap

**Five rounds per branch.** A round that never reaches a clean validator run still counts. At the fifth the branch
stops and reports which findings are open, on which cells, what was tried, and what the real problem probably is. Then
the orchestrator:

- **Reports the capped branch by name**, at the top of its report, before any success. Four clean pages do not make the fifth one fine.
- **Does not merge a knowingly broken page silently.** Merge it and label it, or leave it out and say so.
- **Does not delete the offending cells** to make a check pass, and **does not weaken, skip or edit the validator.** It is not yours to change.
- **Asks.** Five failed rounds means the problem is understanding, not typing.

A page that will not come clean in five rounds is usually one page doing two jobs, and splitting it into two branches
is a legitimate repair. Shrinking labels until a check stops firing is not.

### 5. Merge

The orchestrator merges. Each part is a single page mxfile, so the merge concatenates `<diagram>` elements in the page
order fixed in step 1, never in glob order, because that order is the tab order a reader gets.

**What has to be unique, and what does not.** Cell ids are checked inside one `<root>`, so **they are per page and
never need renumbering on merge**, and two pages may both have an `apigw`. What is checked across the file is the
`<diagram>` `id` and `name`, and a duplicate of either is an error. Both were made unique for free at fan-out, and
nothing is rewritten during the merge, which is why the merge cannot introduce a defect.

```sh
# page order is the list from step 1, not a glob
{
  echo '<mxfile host="app.diagrams.net">'
  for slug in infrastructure functional-flow path-inference path-training path-batch; do
    sed -n '/<diagram /,/<\/diagram>/p' "docs/diagrams/parts/$slug.drawio"
  done
  echo '</mxfile>'
} > docs/diagrams/machinel.drawio
node draw-io-utils/validate-drawio.js docs/diagrams/machinel.drawio
```

**Validate the whole merged file**, not just the parts. It is the only step that can see a duplicate page id
or name. If a part slipped its slug, fix the part and merge again rather than the merged file, or the next merge
overwrites the patch. Keep `parts/` in the repo, it is where the next run starts and where the ledgers live. Then run
the round trip in `reference/drawio.md` once, if the binary is installed.

## The findings ledger

One per branch, `docs/diagrams/parts/<page-slug>.findings.md`, appended never rewritten, so a later fix cannot
silently regress an earlier finding. Each round appends a heading and a row per finding:

```markdown
## Round 2, reviewer verdict: not clean

| # | Rank | What is wrong | Where | Fix applied |
|---|---|---|---|---|
| 1 | blocking | Edge label printed across the SageMaker endpoint icon | infrastructure, e5, label lands at 459,649 | routed via the x=459 corridor, offset y -50 |
```

A finding carries enough to re-check it: what was wrong, where (page, cell id, and the coordinate if it is a placement
defect), and what the fix was. "Layout is crowded" re-checks to nothing. The generator fills the fix column as it
fixes and sees the whole history, and the next reviewer confirms the earlier rows are still fixed.

## The reviewer

The reviewer judges exactly what the checks cannot.

- **Wrong icon for the service.** A real stencil for the wrong thing validates clean.
- **Edge direction contradicting the design.** An arrow pointing the wrong way is a lie the file cannot detect.
- **A connection the design does not have, or one the design has and the page does not.**
- **Text over text or text over a node**, that the validator's shrunken estimate let through, and crowding: a page simply too busy to read.
- **A label that no longer says what happens**, usually because a previous round shortened it.

**It must read the solution design, not only the picture.** A missing connection and a wrong direction are
invisible to anyone holding only the image. It returns a **verdict, clean or not clean**, one word on the first line,
then **ranked findings**, blocking before minor, in the ledger's shape.

**"Looks fine" is not a verdict**, and neither is a clean verdict from a reviewer that did not open the
design. The orchestrator rejects both and respawns. Clean means every component and connection matches the design, and
nothing on the render is unreadable.

## Tiers

In `lets-code`'s vocabulary.

| Role | Tier | Why |
|---|---|---|
| Generator | 2 | Opus medium. Dense and mechanical rather than hard, and it is handed the design, the page scope and `reference/drawio.md`, so the context is already assembled |
| Reviewer | 3 | Opus high. It holds the design and the image at once to find what the checks and the generator both missed, and nothing downstream catches what it lets through |

The orchestrator scopes, merges and reports itself. That is not sub-agent work.

## Pages

One `.drawio` file, several `<diagram>` pages, one branch each. At minimum:

| Page | Contains | Reads as |
|---|---|---|
| Infrastructure | Real cloud service icons, inside account, region, VPC, subnet and availability zone containers | A deployment |
| Functional flow | Plain boxes and labelled edges, no icons at all | Logic |
| One per critical request path | The paths the design names, each showing what happens in order | A trace |

A page exists because it earns its place. Splitting exists so no detail is lost on an overloaded canvas, not to
inflate the page or branch count. Two request paths differing in one hop are one page.

## Ponytail here, precisely

The technical simplification already happened in `lets-design`. Do not redo it. Here ponytail means **simpler to
read**: fewer crossings, straighter routes, fewer nodes per page, splitting a page doing two jobs.

**It never means deleting a fact to reduce clutter.** A fact removed from an edge label lands in a node label:
same information, fewer strokes.

**Shortening labels until a check stops firing is a failure, not a fix.** The check fires because two things
are on top of each other, and the answer is to move one. A diagram that validates and no longer says what happens on
its edges has failed at its one job. Widen the pitch, route through a corridor, offset the label, split the page.
Never trim the truth.

## What the orchestrator reports

Every branch, its round count and its final verdict, **any capped branch first** with its open findings ahead of the
clean ones. Whether pages were reviewed against a render or blind, because a blind run is a weaker claim. The merged
file path and its validator result.

## Handoff

`lets-design` decided it. This skill drew it. `lets-code` builds it. If the diagram is accepted and the next question
is "how do we build it", stop and invoke `lets-code`.
